# Native FUSE3 Workspace Mount (`FsService`) Specification

**Status:** Proposed draft for owner review (synthesized via `/to-spec`; not an approved contract; nothing here is implemented yet).

## Problem Statement

Needy currently mounts an executor's workspace into an actor by launching `sshfs` in passive mode and tunneling SFTP v3 over an exec stream (`Origin::ActorMount`) to `sftp-server` on the executor. Across local, high-latency WAN, and Windows executor topologies, this architecture creates severe reliability, correctness, and performance failures for driving programs:

1. **Unmaintained and external dependencies.** Upstream `libfuse/sshfs` has been archived read-only since May 2022, and every executor must ship an OpenSSH `sftp-server` binary.
2. **Severe WAN performance collapse.** Live probes across a ~207 ms RTT Linux-to-Linux link showed sequential cold reads collapsing to ~0.10 MB/s (3,345× slower than loopback), 200 small-file creates taking ~291 s (~7 serial RTTs per file), and cold 500-file walks taking ~9.6 s.
3. **Hidden stale-cache window.** Although mount options request 1-second kernel attribute/entry timeouts, enabling `sshfs` userspace caching silently applies a 20-second userspace cache timeout, serving stale metadata for up to 20 seconds.
4. **Broken Windows executor POSIX semantics.** Live probes mounting a Windows 11 executor via `sftp-server.exe` failed on fundamental developer-tool operations: unlinking or atomically replacing an open file returns `EPERM`, single-writer SQLite `DELETE` mode fails with `disk I/O error` (and two writers hang), case-insensitive path aliasing creates distinct synthetic FUSE inodes that silently truncate reads to stale cached sizes, `chmod +x` is silently dropped, and symlinks created from Linux fail `readlink` and `open` with `EPERM`.
5. **Broken absolute symlinks and cross-boundary locking on Linux.** Creating an absolute symlink over `sshfs` fails `readlink` with `EPERM`, and SFTP v3 has no lock protocol, so `flock`/`fcntl` locks never propagate across the actor-executor boundary.
6. **Silent-write hazard on disconnect and fragile fault injection.** When the backing `sftp-server` dies abruptly, `sshfs` unmounts and external path lookups silently fall through to the empty underlying directory; when `sshfs` itself crashes, the mount remains stuck until lazy unmount. Meanwhile, the daemon's file-domain fault interceptor must parse raw SFTP packets inside an opaque byte stream.

## Solution

Replace `sshfs` + `sftp-server` with an **in-process, async Rust FUSE3 workspace mount** speaking a **typed gRPC `FsService` protocol** between the actor side (VM guest init or host-side container mount) and the executor (local or remote runner, Linux/macOS/Windows):

- **Single unified transport and binary.** Both the FUSE3 client (built on upstream `fuse3` `raw::Filesystem`) and the executor-side filesystem server live inside Needy itself, eliminating `sshfs` and `sftp-server` subprocesses and working uniformly across `linux-firecracker`, `macos-vz`, `linux-container` (non-root via `fusermount3`), and `macos-apple-container` actors, as well as Linux, macOS, and Windows executors.
- **High-latency WAN performance built in from day one.** Enable kernel `writeback_cache`, `force_readdir_plus`, and high `max_background` concurrency; pair them with an adaptive multi-stage sequential prefetcher with a small backward-seek window, a bounded TTL negative-lookup cache, per-handle async write-back batching, and compound RPCs for small-file operations.
- **First-class POSIX fidelity on Linux and Windows.** On Linux executors, anchor every inode with `O_PATH` file descriptors and `openat2(RESOLVE_IN_ROOT | RESOLVE_NO_MAGICLINKS)` so symlinks cannot escape the workspace and open-unlinked or renamed files keep working. On Windows executors, open handles with `FILE_SHARE_DELETE`, use Win10 1903+ `POSIX_SEMANTICS` disposition/rename APIs, and map real NTFS `FileId` values to FUSE inodes so atomic replace, open-file unlink, SQLite, and case-insensitive access remain coherent.
- **Typed file-domain fault interception and clean disconnect lifecycle.** The control daemon intercepts typed `FsService` RPCs directly by operation and actor-relative path instead of parsing SFTP byte streams, and mount sessions enforce bounded reconnect windows, explicit `ForceUnmount` cleanup, and fail-fast `EIO` without silent local fallthrough.

## User Stories

1. As a driving program running in a `linux-firecracker` actor, I want my workspace mounted without relying on external `sshfs` or `sftp-server` binaries, so that runs have fewer host/image dependencies and no unmaintained FUSE wrapper.
2. As a driving program running in a non-root `linux-container` actor, I want the exact same FUSE3 workspace mount via `fusermount3`, so that non-root hosts without KVM get identical workspace semantics to VM actors.
3. As a driving program running in a `macos-vz` or `macos-apple-container` actor, I want the same FUSE3 client protocol inside the guest, so that macOS and Linux actors share one mount implementation and behavior contract.
4. As a user running an actor across a 50–250 ms WAN link to a remote executor, I want sequential cold reads of large files to scale up automatically through adaptive prefetching, so that reading artifacts or source archives does not collapse to sub-megabyte speeds.
5. As a user running an actor across a high-latency link, I want sequential and buffered writes to pipeline asynchronously via kernel writeback caching and per-handle write-behind batching, so that large writes achieve near-link throughput instead of stalling per FUSE write chunk.
6. As a user running `git status`, `find`, or language servers over a remote workspace, I want directory listings to return entries and attributes together via `readdirplus`, so that cold directory walks do not pay an extra round trip per file.
7. As a user whose build tools probe many non-existent paths (`node_modules`, header search paths, Python imports), I want a bounded TTL negative-lookup cache on the FUSE client, so that repeated `ENOENT` probes do not amplify into WAN RTT storms.
8. As a user creating many small files (builds, package installs, test fixtures) over a remote workspace, I want small-file create/write/close and read flows to use writeback and compound RPCs, so that small-file throughput is not crippled by 5–7 serial round trips per file.
9. As a user editing files on the executor while an actor is running, I want metadata and negative caches to expire within the configured short TTL (no hidden 20-second userspace cache), so that newly created or updated files become visible promptly.
10. As a driving program running on Linux against a Windows executor, I want `unlink` on an open file and atomic `rename`/`replace` over an open target file to succeed, so that `git`, editors, and build tools do not fail with `EPERM`.
11. As a driving program running SQLite (`DELETE` or `WAL` journal mode) in a workspace hosted on a Windows executor, I want single-writer and concurrent commits to succeed without `disk I/O error` or hangs, so that agent state databases and test suites work reliably on Windows executors.
12. As a driving program accessing files with mixed casing on a case-insensitive Windows executor, I want both lookup names to resolve to the same NTFS `FileId`-backed FUSE inode, so that writing via one casing and immediately reading via another never truncates data to a stale cached size.
13. As a driving program creating relative or absolute symlinks inside a workspace, I want `symlink` and `readlink` to preserve the target string faithfully without spurious `EPERM` errors, so that symlink-heavy ecosystems (`pnpm`, `nix`, toolchains) function correctly.
14. As a driving program running scripts in a workspace hosted on a Windows executor, I want `chmod +x` behavior to be explicitly defined and consistent (either persisted via metadata/policy or clearly documented), so that executable permissions are not silently lost without notice.
15. As a driving program receiving invalid-filename errors on a Windows executor (such as `?` or `\`), I want clear POSIX `EINVAL` errors and explicit rejection of NTFS Alternate Data Stream colons (`:`), so that tools do not misdiagnose invalid paths as `ENOENT` or create hidden host ADS files.
16. As an operator running an executor on Linux, I want the executor FS server to prevent symlink escapes outside the workspace root using `openat2` and `O_PATH` file descriptors and to refuse opening host device nodes or FIFOs, so that a compromised actor cannot escape its workspace or hang the executor.
17. As a user running concurrent tools across an actor and an executor (or two actors sharing one workspace), I want an opt-in remote POSIX lock mode backed by Linux `F_OFD_SETLK`, so that cross-boundary file locking is genuine when needed without penalizing single-actor SQLite latency by default.
18. As a user running single-actor SQLite workloads over a high-latency link, I want the default workspace lock mode to enforce locks locally in the kernel VFS, so that SQLite transactions do not pay a WAN RTT on every lock state transition.
19. As a user running a read-only workspace mount (`writable: false`), I want mutating FUSE operations rejected cleanly with `EROFS` at both client and server boundaries, so that read-only inputs are strictly protected.
20. As a user experiencing a transient runner tunnel drop, I want the FUSE3 mount to hold or cleanly recover within the run's reconnect grace window and fail in-flight operations with `EIO` rather than hanging forever, so that a brief network blip does not permanently brick the actor's working directory.
21. As an operator whose remote executor dies permanently or whose run is stopped, I want the FUSE3 mount to fail closed and detach cleanly (via control-plane `ForceUnmount` and `fusermount3 -u -z` fallback), so that processes never silently write into an unmounted local directory and no zombie mounts remain.
22. As a user writing `file` domain chaos rules in a profile (such as injecting `EIO`, `ENOSPC`, or latency on matching paths), I want the daemon to intercept typed `FsService` RPCs directly instead of parsing SFTP byte streams, so that file-fault rules are exact, auditable, and cover every file operation cleanly.
23. As a user inspecting `needy run report` and trace events, I want workspace mount lifecycle events, cache/fault injections, and transport errors recorded with structured fields, so that I can diagnose slow or failing file operations from traces alone.
24. As an operator running mixed versions during rollout, I want a clear compatibility boundary (or explicit fallback/error) between executors that advertise `FsService` and older ones that do not, so that upgrades fail predictably rather than hanging silently.

## Implementation Decisions

- **FUSE client library choice:** Use upstream `Sherlock-Holo/fuse3` (`v0.10.0+`, Rust 2024, `zerocopy` + `write_vectored`) implementing the low-level inode-based **`raw::Filesystem`** trait—not `PathFilesystem` (which breaks hardlinks and `batch_forget` refcounting) and not `rfuse3` (an older `bincode` fork with unwired buffer pooling and broken `file-lock` examples). If cross-boundary BSD `flock(2)` is later required, apply a targeted upstream patch for `FUSE_FLOCK_LOCKS` (currently commented out in `fuse3`), rather than switching libraries.
- **Mount flags & kernel negotiation:** Negotiate `FUSE_WRITEBACK_CACHE` (`write_back(true)`), `FUSE_DO_READDIRPLUS` (`force_readdir_plus(true)`), `FUSE_ASYNC_READ`, `FUSE_BIG_WRITES`, `FUSE_MAX_PAGES`, and `max_background = 64` (configurable). Keep `default_permissions` enabled and enforce explicit `uid`/`gid` ownership mapping matching the profile user, with a single consistent short metadata TTL (default 1 s) and **no** hidden multi-second userspace cache layer.
- **WAN read & write data path (preventing naive FUSE regressions):**
  - *Adaptive sequential prefetcher* (adapted from `mountpoint-s3`): issue an initial read of `1 MiB + 128 KiB` (absorbing Linux's extra 128 KiB kernel readahead in one RTT), trigger the next stage once half the window is consumed, double the read window up to a bounded ceiling on queue stall, and maintain a small backward-seek ring buffer (1 MiB) plus forward-skip tolerance so out-of-order kernel readahead does not cancel active prefetch streams.
  - *Write-back & flush semantics* (adapted from `datenlord`, `mountpoint-s3`, and `virtiofsd`): under `FUSE_WRITEBACK_CACHE`, open write-only handles on the server as `O_RDWR` and strip `O_APPEND` (since the kernel owns writeback offsets); batch dirty writes per open handle with an async write-behind worker flushed on `flush`/`fsync`/`release`; guard `flush` finalization against `fork` children and zero-byte `dup+close` patterns while surfacing real write errors on `close(2)`.
  - *Compound RPCs & negative cache*: provide compound `CreateAndWrite` / `ReadWhole` fast-path RPCs for small files, `ReadDirPlus` returning full directory entries + attributes in one RPC, and a bounded FIFO-expiring `NegativeCache<(parent_ino, name)>` sharing the short metadata TTL (invalidated immediately on local `create`/`mkdir`/`symlink`/`rename`).
- **Typed `FsService` gRPC contract (`api-proto`, `api-client`, `api-server`):**
  - Define a dedicated `FsService` (provisional name) multiplexed over the existing guest/runner gRPC channel rather than tunneling an opaque binary protocol over `ExecStream`.
  - Include session handshake (`Mount`, negotiating root inode, capabilities, read-only flag, and lock mode), inode/path operations (`Lookup`, `GetAttr`, `SetAttr`, `ReadDirPlus`, `Open`, `Read`, `Write`, `Flush`, `Fsync`, `Release`, `Create`, `Mkdir`, `Unlink`, `Rmdir`, `Rename`, `Symlink`, `ReadLink`, `Link`, `StatFs`, `Forget`/`BatchForget`), optional lock RPCs (`GetLock`, `SetLock`), and a bidirectional session heartbeat / `ForceUnmount` control stream (adapted from `neutree-ai/afs`).
- **Executor-side Linux FS server (adapted from `virtiofsd` `PassthroughFs`):**
  - Validate every single-component filename (rejecting empty, `/`, `.`, `..`; clamping `..` at workspace root).
  - Resolve children via `openat2(RESOLVE_IN_ROOT | RESOLVE_NO_MAGICLINKS)` with `O_NOFOLLOW | O_CLOEXEC` (falling back to `openat` on older kernels) and pin every live inode with an `O_PATH` file descriptor indexed by `(dev, ino, mnt_id)`.
  - Enforce an `is_safe_inode` gate allowing only regular files, directories, and symlinks (blocking host devices, sockets, and FIFOs), and reopen `O_PATH` fds through `/proc/self/fd`.
  - Maintain strict non-zero CAS reference counting on inodes (forbidding `0 -> 1` resurrection) with `saturating_sub` eviction on `Forget` / `BatchForget`, and use `dup()` + `close()` on `Flush` to surface deferred host write errors.
  - Implement server-side POSIX locks using Linux Open File Description locks (`F_OFD_GETLK` / `F_OFD_SETLK` / `F_OFD_SETLKW` with `l_pid = 0`) scoped per server file handle so a single multi-client executor process never clobbers or prematurely releases another handle's locks.
- **Executor-side Windows FS server:**
  - Open all file handles with `FILE_SHARE_READ | FILE_SHARE_WRITE | FILE_SHARE_DELETE`.
  - Implement `Unlink` using `SetFileInformationByHandle(FileDispositionInfoEx)` with `FILE_DISPOSITION_POSIX_SEMANTICS | FILE_DISPOSITION_IGNORE_READONLY_ATTRIBUTE` and `Rename` using `FileRenameInfoEx` with `FILE_RENAME_POSIX_SEMANTICS | FILE_RENAME_REPLACE_IF_EXISTS` (Windows 10 1903+), fixing open-file unlink, atomic replace over open targets, and SQLite `DELETE` mode.
  - Derive stable FUSE inode numbers from real NTFS `FileId` (`FILE_ID_INFO`) and canonicalize case on lookup to eliminate split-brain FUSE caching between mixed-case aliases.
  - Explicitly reject NTFS Alternate Data Stream colons (`:`), trailing dots/spaces where unsafe, and invalid Win32 characters with `EINVAL` (never `ENOENT`).
  - Handle symlinks cleanly (preserving relative POSIX targets in `ReadLink`, returning clear `EPERM` when the Windows host lacks symlink creation privilege) and define an explicit execute-bit policy (e.g., default executable/mode synthesis or sidecar metadata—see Further Notes).
- **Configurable lock mode (provisional schema):**
  - Default to **local** VFS locking (`lock_mode: local`) so single-actor workloads (including SQLite over WAN) pay zero network RTT per lock transition.
  - Support opt-in **remote** locking (`lock_mode: remote`) per workspace mount for multi-actor or actor+executor concurrent access, forwarding `FUSE_POSIX_LOCKS` to the server's `F_OFD_SETLK` (Linux) or server-side advisory lock table (Windows, avoiding Win32 mandatory `LockFileEx` blocking host readers).
- **Daemon file-domain interception & lifecycle:**
  - Move `needy-core`'s file-domain interceptor (`file.open` and future `file.read`/`file.write`/`file.stat` hooks) from an SFTP stream parser to a typed `FsService` interceptor in the daemon relay, matching faults against actor-relative workspace paths.
  - On disconnect, pause or fail in-flight RPCs with `EIO` within the reconnect window, rebuild stateless path-anchored mounts or cleanly tear down the FUSE session on expiry/run stop via `ForceUnmount` + `fusermount3 -u -z`, and never leave the mountpoint silently writable as a local directory.
- **Migration & fallback boundary:**
  - Keep the existing `sshfs` mount path behind a temporary feature/fallback toggle only during rollout until `FsService` passes the full non-root e2e matrix; remove `sshfs` and `sftp-server` once parity is verified, and surface a clear diagnostic error if a profile requests `FsService` against a runner that does not advertise it.

## Testing Decisions

- **Primary testing principle:** Test observable POSIX filesystem behavior, cross-boundary invariants, fault injection effects, and latency/throughput regressions through public boundaries—never assert on internal cache maps, private structs, or mocked FUSE wire frames unless testing a pure component in isolation.
- **Proposed test seams (minimal, highest-level seams):**
  1. **Seam 1 — In-process `FsService` contract suite (highest pure-Rust seam, zero FUSE kernel needed):** Exercise the real Linux and Windows executor FS server implementations directly through the `FsService` trait/gRPC server (and through the daemon's typed file-fault interceptor) for symlink-escape rejection, `O_PATH` open-unlinked/rename semantics, `F_OFD_SETLK` multi-handle lock isolation, Windows `POSIX_SEMANTICS` unlink/replace + `FileId` case-aliasing coherence, `Forget` refcounting, and `file.open` fault injection.
  2. **Seam 2 — Real Linux FUSE3 end-to-end harness (`cargo xtask e2e` + controlled-RTT loopback/WAN proxy):** Mount a real `fuse3` workspace via `needy` (non-root daemon, covering both `linux-firecracker` and `linux-container` drivers) and run an automated POSIX & WAN regression suite against the mountpoint: 500-file cold `walk+lstat`, 200×4 KB create/write/close, 32 MB sequential cold read & write under simulated 50 ms RTT, SQLite `DELETE` and `WAL` concurrent writers, relative & absolute symlinks, open-unlinked & atomic replace, `lock_mode: local` vs `remote`, and abrupt executor kill (`ENOTCONN` + clean unmount, zero zombie mounts).
  3. **Seam 3 — Cross-OS live matrix (`cargo xtask e2e` with remote Windows executor):** Run the Windows POSIX subset (case-aliasing read-after-write, open-file unlink/replace, SQLite `DELETE`/`WAL`, invalid-name `EINVAL`, binary fidelity) against a real Windows executor runner.
- **Prior art in the codebase:**
  - Daemon in-process tests through `needy-api-server` traits (runs, relay, routing, file faults).
  - Non-root host matrix in `xtask` (`cargo xtask e2e`), where real actors, mounts, and remote runners are verified end to end.
  - Prototype benchmark & correctness methodology established during the 2026-11-26/27 cross-host probes (0 ms loopback, 50 ms controlled RTT, ~207 ms WAN, and Linux ↔ Windows 11).

## Out of Scope

- **Kernel `v9fs` (`9P2000.L` over `trans=fd`)** — requires `CAP_SYS_ADMIN` (breaks non-root `linux-container` actors), lacks `READDIRPLUS`, and cannot cleanly reconnect stateful kernel `fid`s across WAN drops.
- **`virtio-fs` (`virtiofsd`) as the primary workspace transport** — rejected upstream by Firecracker (`firecracker#1180`) and limited to co-located local hosts; an optional `macos-vz` (`vfkit`) local `virtio-fs` fast path when no file faults are active is deferred.
- **FUSE ABI 7.40+ features (`FUSE_PASSTHROUGH`, `FUSE_IO_URING`)** — not yet supported by `fuse3` (ABI 7.31) and unnecessary for remote/gRPC-backed workspaces.
- **Bidirectional eventual-consistency sync (Mutagen-style)** — violates strong read-after-write consistency between actors and executors and cannot support live I/O fault injection.
- **Inherent Windows NTFS limitations** — renaming a directory while a descendant handle is open (`EACCES`), coexisting distinct `foo.txt` and `FOO.TXT` entries in one default case-insensitive directory, storing raw Win32-forbidden characters without escaping, and native symlink creation on Windows hosts without Developer Mode / `SeCreateSymbolicLinkPrivilege`.
- **Cross-host BSD `flock(2)` forwarding in v1** — deferred until `FUSE_FLOCK_LOCKS` is enabled in `fuse3`; v1 covers POSIX byte-range locks (`fcntl` / `F_OFD_SETLK`).
- **macOS host-side FUSE mounting via macFUSE kext** — macOS actors (`macos-vz`, `macos-apple-container`) run Linux guests and mount FUSE3 inside the Linux guest; native macOS host FUSE mounting is not required.

## Further Notes

- **Evidence backing this specification (probes, 2026-11-26 to 2026-11-27):**
  - *Linux WAN `sshfs` probe* (Debian 13 x86_64 cloud VM ↔ Debian 13 x86_64 KVM host, 207.3 ms avg RTT): cold 32 MB read 0.10 MB/s (321 s), 200×4 KB create 290.9 s, cold 500-file walk 9.58 s, SQLite `DELETE` timed out (24/100 rows), absolute `readlink` failed with `EPERM`, and `cache=yes` silently held stale `lstat` entries past `attr_timeout=1`.
  - *Linux ↔ Windows 11 `sftp-server.exe` probe* (Debian 12 x86_64 VM ↔ Windows 11 26100 host, ~96 ms bridged RTT): open-file `unlink` and `os.replace` returned `EPERM`, SQLite `DELETE` failed with `disk I/O error`, mixed-case lookup caused silent read truncation (`"upper"` instead of `"upper_updated"`), `chmod +x` was silently dropped, and `readlink` returned `EPERM`.
  - *`fuse3 0.8.1` prototype probe* (Debian 13 x86_64 KVM workstation, Linux 7.1.3, 0 ms vs 50 ms controlled RTT): confirmed 1.94× faster cold 500-file walks via `ReadDirPlus` and working cross-boundary `F_OFD_SETLK` locks, while proving that a naive synchronous `fuse3` implementation regresses 54× on 50 ms WAN writes (2.37 vs 127.9 MB/s) and 6.2× on WAN SQLite `WAL` when every lock hits the network—directly motivating mandatory `writeback_cache`, write-behind pipelining, and `lock_mode: local` default in this spec.
- **Open questions for owner review before implementation:**
  1. **Windows `+x` mode bits:** Should the Windows FS server synthesize executable bits by mount option/extension (simple, zero host side effects) or persist POSIX mode bits in a sidecar/metadata map?
  2. **Reconnect behavior on open file handles:** When a runner tunnel drops and recovers within the grace window, should open handles transparently reopen by anchored relative path (best-effort) or fail with `EIO` (strict, matching current SFTP reconnect behavior) while paths recover immediately?
  3. **Rollout phasing:** Land Linux executor + `FsService` + `fuse3` client first (Slice 1), then Windows `POSIX_SEMANTICS` executor server (Slice 2), then remove `sshfs` + SFTP stream filter (Slice 3)?
